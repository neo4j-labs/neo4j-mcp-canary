## v0.7.0 - 2026-09-25
### Added
* Added multi-instance HTTP mode: a config file can now declare a neo4j_instances list, each with its own Neo4j connection details and auth, letting one running server serve several Neo4j instances at once. A client selects an instance via its own URL path ("/<name>/mcp"), never a header or query param, so each instance's identity and auth are unambiguous. Three connection-auth types are supported per instance: basic (a static service-account username/password baked into that instance's driver, gated by a required client-presented API key so nobody can ride on the shared account unauthenticated), basic_passthrough (the client's own HTTP Basic credentials are forwarded to Neo4j, exactly like existing single-instance HTTP mode), and bearer (the client's Bearer token is verified against that instance's configured identity provider's JWKS endpoint - issuer, audience, signature, and expiry - before being forwarded to Neo4j). Bearer-type instances also serve their own RFC 9728 protected-resource metadata document, so a spec-compliant MCP client can discover which identity provider to log in with before ever presenting a token. The instances list is deliberately configurable only via the config file, never an environment variable or CLI flag, since it is inherently a list rather than a single value; config-file secrets may reference ${ENV_VAR} for interpolation alongside plaintext values.
* Multi-instance HTTP mode's config file entries can now optionally declare an embedding block naming a Neo4j GenAI plugin provider (openai, azure-openai, vertexai, or bedrock-titan) and its configuration (API credentials, model, etc.). The set-vector-property tool gains a text field: when supplied instead of a pre-computed vector, the server generates the embedding itself via Neo4j's ai.text.embed function, using that instance's configured provider, before storing it. There's no dedicated local-LLM provider, but the openai provider's target URL is configurable on the Neo4j server itself, so it can be redirected to an OpenAI-compatible local server (e.g. LM Studio, Ollama) - see docs/MULTI_INSTANCE.md. An instance with no embedding configured can still store vectors via the existing vector field.
* The search category's set-vector-property tool now checks a generated or caller-supplied vector's dimensions against any existing matching vector index before writing (via Neo4j's SHOW INDEXES options column), rejecting a mismatch with a clear error instead of silently storing a vector the index can't use. A new check-embedding-dimensions tool lets a caller validate a configured embedding provider/model against a vector index's dimensions up front, without writing anything.
* STDIO and single-instance HTTP mode can now configure a GenAI embedding provider too, via the NEO4J_MCP_EMBEDDING_PROVIDER/NEO4J_MCP_EMBEDDING_CONFIGURATION environment variables (or their --neo4j-mcp-embedding-* CLI flags) — the same set-vector-property text field and check-embedding-dimensions tool that previously only worked in multi-instance HTTP mode now work everywhere.
* The openai embedding provider (used by set-vector-property's text field and check-embedding-dimensions) is now generated by this MCP server itself, via a direct HTTP call to an OpenAI-compatible /embeddings endpoint, instead of going through Neo4j's ai.text.embed. An optional configuration.baseUrl key redirects it to any OpenAI-compatible local server (LM Studio, Ollama) with no Neo4j-side GenAI plugin or configuration needed at all. The other three providers (azure-openai, vertexai, bedrock-titan) are unaffected and still generated by Neo4j's ai.text.embed, reusing the auth schemes it already implements.
